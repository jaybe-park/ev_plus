# 전체 리뷰 (ev_plus)

Task 단위 검증을 전부 통과했는데도 **전체가 틀어진 곳**을 찾는다. 절차 순서는 바꾸지 않는다.

## 1. 인터뷰 (먼저, 생략 금지)
사람에게 묻는다(AskUserQuestion). 답은 보고서 앞머리에 기록해 모든 리뷰어의 공통 전제로 쓴다.
- 지금 성공 기준은? (예: 봇이 사람 상대로 쓸 만한 수준 / 힌트가 믿을 만함 / 혼자 오래 유지 가능)
- 요즘 불안한 점, 다음 마일스톤
- 문제 제기 불필요한 것(의도적으로 받아들인 한계)

## 2. 관점별 병렬 리뷰 (⚙ 기본 4개, `CLAUDE.md` 프로젝트 값)
Agent 도구로 동시에 띄운다(읽기 전용). 이 프로젝트 기본 관점:

| 관점 | 찾는 것 |
|---|---|
| 게임 정확성 | 룰·칩 보존·사이드팟·이벤트 순서가 엔진↔서버↔프론트에서 같은 사실을 말하는가 |
| 봇·힌트 신뢰성 | GTO/에퀴티 데이터 오염, 캐시 드리프트, 봇 판단 경로별(easy/medium/hard) 불일치 |
| 원칙↔구현 대조 | spec·ADR의 "확정" 규칙이 코드·시드·기본값에서 실제로 지켜지는가, 장치 없는 규칙 |
| 지속가능성·검증 체계 | 테스트가 보장하는 것/못 하는 것, 문서 모순·낡음, DB 성장, 맥락 복원 비용 |

리뷰어 공통 지시(프롬프트에 그대로 넣는다):
- 단순 코드 리뷰가 아니라 로직 모순, 프로세스 부재, 구조적·근원적 문제를 찾는다.
- 인터뷰 기록을 판단 전제로 쓴다.
- 읽기 전용. 서버·DB·git 쓰기 금지. 비밀정보 파일(.env, ssl/) 열람 금지.
- 발견마다: 제목 / 심각도(치명·높음·중간·낮음) / 관찰(파일:줄) / 누가 어떤 상황에서 겪나 / 근원 원인 / 권고. 확인·추정 구분.
- 상세는 스크래치패드 파일로, 최종 응답은 상위 10개 요약.

## 3. 교차 검증
- 여러 관점이 같은 곳을 가리킨 발견 표시(신뢰도 높음)
- 치명·높음은 메인 세션이 **직접 코드로 재확인**. 틀린 주장은 정정 기록.

## 4. 근본 원인으로 재구성
발견을 원인별로 묶는다.

## 5. 보고서 — `self-reviews/YYYY-MM-DD.md`
한 페이지 결론 → 성공 기준별 판정 → 근본 원인 → 권고 로드맵(비용 작은 것부터) →
**사람이 내릴 결정 목록** → 잘 된 점 → 재확인 기록 → 부록(관점별 원문 요약).

## 6. 착수하지 않는다
보고서만 쓰고 멈춘다. 사람이 읽고 memo/DECISIONS/TODO로 옮긴 것만 실행된다.
보고서 파일만 커밋한다(`git add -- self-reviews/<파일>`).

## 비용
사용량 한도의 95%에 닿으면 즉시 중단하고 그때까지 찾은 것만 기록한다.
