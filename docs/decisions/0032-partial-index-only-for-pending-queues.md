# 0032. 대기 큐 인덱스는 부분 인덱스로만, 인덱스 삭제 전 EXPLAIN QUERY PLAN 확인

- 상태: 대체됨 → 0034
- 날짜: 2026-07 (v7, v8, v10에 걸쳐 확립) · 결정자: jaybe-park

## 맥락
`equity_cache`는 계속 커지는데(당시 700만 행 이상, 현재 수천만~1억 행대) 워커의 "다음 작업" 선택 쿼리는 항상 `exact=0`인 소수 대기 행만 찾는다. v8에서 조건 없는 전체 인덱스(`idx_equity_street`, 766만 행)를 "잉여"로 보고 지웠는데, 실제로는 프리플랍 대기 체크 쿼리 하나가 그 인덱스에 의존하고 있었다. 그 결과 이미 100% 완료라 항상 0건을 반환하는 쿼리가 매 배치 호출마다 전체 테이블(1억 행)을 3.1초씩 풀스캔했고, v10에서야 발견해 복구했다.

## 결정
행 수가 계속 늘고 조회는 소수 조건(`exact=0` 등)에만 걸리는 큐 성격의 테이블에는 **부분 인덱스**(`WHERE exact=0 AND ...`)만 만든다. 조건 없는 전체 인덱스는 만들지 않는다 — 승격/완료된 행이 인덱스에서 자동으로 빠지므로 인덱스가 항상 작게 유지된다. 인덱스를 하나라도 지울 때는 "잉여로 보인다"는 판단만으로 지우지 않고, 그 인덱스를 탈 가능성이 있는 모든 쿼리에 대해 `EXPLAIN QUERY PLAN`으로 실제 계획을 확인한 뒤 지운다.

## 버린 대안
- 조건 없는 전체 인덱스(커버링 인덱스 포함) — 테이블이 커질수록 다시 느려지고 쓰기 비용만 늘어난다.
- "코드 사용처가 안 보이니 잉여" 판단만으로 인덱스 삭제 — v8 사고의 직접 원인.

## 결과
- 영향받는 spec: `docs/spec/db.md`
- 강제 장치: 없음(테스트 후보 — 워커의 각 작업 선택 쿼리에 대해 임시 스키마 DB로 `EXPLAIN QUERY PLAN`에 `SCAN`이 없는지 assert).
