# 0020. SQLite 쓰기 원칙 — 쓰기는 메인 프로세스, 계산만 Pool, 짧은 트랜잭션, 멱등 저장

- 상태: 유효
- 날짜: 2026-07-10 · 결정자: jaybe-park

## 맥락
그라인드(아레나 + 워커 동시 실행) 중 SQLite 쓰기 락 경합이 반복됐다(2026-07-07~08, 여러 커밋). 원인은 봇이 결정마다 커밋, 기록기가 트랜잭션을 오래 잡음, 커넥션 누수였다. 이후 워커가 단일 프로세스라 멀티코어의 약 80%가 놀고 있었는데, SQLite는 여러 프로세스가 동시에 쓰는 것이 근본 제약이다.

## 결정
- **쓰기(캐시 조회·저장)는 워커 메인 프로세스 1개만** 한다. `multiprocessing.Pool`에는 DB에 닿지 않는 순수 계산(리버 전수조사, MC 샘플)만 보낸다. 턴·플랍 DP는 자식 캐시를 메인에서 일괄 조회한 뒤 미적중 자식만 Pool로 계산하고 메인에서 일괄 저장한다.
- `--workers 1` 순차 경로를 유지한다(병렬 결과와 같아야 하는 회귀 기준·디버깅용).
- 커넥션은 열고-쓰고-닫는다. 모든 커넥션은 WAL + `busy_timeout` 30초.
- 봇의 MC 기여는 메모리에 모았다가 25스팟마다 한 번에 커밋한다. 게임 기록기는 액션을 버퍼링했다가 핸드 종료 시 한 트랜잭션으로 쓴다.
- 워커 저장은 멱등이다(`WHERE id=? AND exact=0`) — 다른 프로세스가 먼저 끝낸 행은 조용히 건너뛴다.
- 워커끼리, 그리고 그라인드·튜닝 같은 무거운 작업은 동시에 돌리지 않는다.

## 버린 대안
- 워커 프로세스가 각자 DB에 쓰기 — SQLite 동시 쓰기 제약으로 락 경합.
- 서버형 DB(MySQL 등)로 전환 — 로컬 단일 사용자 패턴에서 운영 부담 대비 이득이 없다.

## 결과
- 영향받는 spec: `docs/spec/equity.md` (DB 공통 규칙은 DB spec)
- 강제 장치: 동시 실행 금지는 `tests/test_workflow.py::test_exclusive_runs`(Claude Code hook — 에이전트 실행만 막고 사람이 직접 실행하면 장치 없음). `--workers 1`/`N` 결과 일치, 커넥션 누수는 장치 없음(1회 수동 검증).
