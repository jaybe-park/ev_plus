# 0033. 공유 운영 DB에 직접 쓰지 않는다 — 스크립트 경유

- 상태: 유효
- 날짜: 2026-07-10~17 · 결정자: jaybe-park

## 맥락
운영 중인 `poker.db`에 대해 여러 차례 수동 개입이 있었다: 체크포인트를 DB 기준으로 긴급 재구성, 미수집 큐 항목의 `collected`를 손으로 `1`로 갱신, 오탐 데이터 53건을 손으로 삭제, v11에서 손상된 GTO 테이블을 통째로 `DROP`. 모두 그 상황에서는 의도된 정당한 조치였지만, 매번 `sqlite3` CLI나 즉석 파이썬 스니펫으로 직접 실행했고 되돌릴 장치나 사전 확인(dry-run) 없이 이뤄졌다.

## 결정
공유 운영 DB(`poker.db`)에 대한 삭제·갱신·구조 변경은 사람이 `sqlite3` CLI나 즉석 스니펫으로 직접 실행하지 않고, 가능하면 `--dry-run`을 지원하는 스크립트를 통해서만 한다. 스키마 변경은 `db/schema.py`의 마이그레이션 메커니즘을 통해서만 한다(임시 `ALTER`/`DROP`을 직접 실행하지 않는다).

## 버린 대안
- 기존처럼 필요할 때마다 CLI로 직접 조작 — 매번 되돌릴 수 없는 실수 위험을 안고 간다.

## 결과
- 영향받는 spec: `docs/spec/db.md`
- 강제 장치: 없음. 조직 가드레일 R2(DB 파괴/대량변경 차단)가 에이전트의 실행은 막지만, 사람이 터미널에서 직접 실행하는 것은 막지 못한다. 차단 hook 추가는 TODO 후보(findings 참고).
