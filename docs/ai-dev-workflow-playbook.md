# AI 에이전트 개발 운영 플레이북

> **목적**: 사람 1명이 AI 코딩 에이전트(Claude Code 등)로 서비스를 만들고 유지할 때, 몇 달이 지나도 에이전트가 맥락을 정확히 복원하고 사람이 결과를 검증할 수 있게 하는 **문서·작업 흐름·검증 장치**의 표준.
> **전제**: **빈 프로젝트에 적용하는 정상 운영 상태의 규칙**이다. 특정 프로젝트 내용이 없으므로 이 파일을 복사하고 §8 "도입 절차"를 따르면 된다.
> **기존 프로젝트**(문서가 이미 쌓인 저장소)는 먼저 [ai-dev-workflow-migration.md](ai-dev-workflow-migration.md)로 이 구조로 옮긴 뒤 이 플레이북을 따른다.
> **출처**: dataspace 프로젝트 종합 점검(2026-09-26)에서 드러난 문제(문서 모순 누적, 원칙-구현 불일치, 결정 대기 분산, 저장소 밖 규칙)를 일반화했다.

---

## 1. 전제 — 유지보수 주체가 바뀌었다

이 플레이북은 다음 유지 모델을 전제한다.

- 코드를 쓰고 고치는 주체는 **AI 에이전트**다.
- 사람(감독자)은 **코드를 읽지 않거나 거의 읽지 않는다.** 결정하고, 결과를 확인한다.
- 에이전트는 **세션마다 기억이 없다.** 저장소에 적힌 것만 안다.

그래서 좋은 저장소의 기준이 바뀐다.

| 예전 기준(사람이 유지) | 이 플레이북의 기준(AI가 유지) |
|---|---|
| 사람이 읽기 쉬운 코드 | **에이전트가 새 세션에서 짧은 문서만 읽고 현재 상태를 정확히 복원**할 수 있는가 |
| 코드 리뷰로 품질 확보 | **기계적 장치(테스트·hooks·CI)와 검증·리뷰 에이전트**로 품질 확보 |
| 규칙은 문서로 공유 | **규칙은 장치로 강제**, 문서는 장치가 없는 것만 |

## 2. 불변 원칙과 기본값

이 플레이북의 내용은 두 종류다.

- **🔒 불변 원칙** — 프로젝트와 무관하게 지킨다. 바꾸면 이 플레이북을 쓰는 의미가 없어진다.
- **⚙ 기본값** — 수치·폴더 이름·템플릿 항목·도구 선택. 프로젝트 규모·팀·런타임에 맞게 **조정한다.** 조정한 값은 프로젝트 `CLAUDE.md`의 "프로젝트 값" 절에 적는다(§5). 전체 목록은 §9.

기본값을 비워 두지 않는다. "프로젝트가 알아서 정한다"로 두면 대부분 아무것도 정하지 않는다 — 그래서 기본값을 주고, 바꿀 수 있다고 명시한다.

### 🔒 불변 원칙 6가지

1. **문서는 성격별로 나눈다** — 현재 상태 / 결정 / 이력을 한 파일에 섞지 않는다(§3).
2. **현재 상태 문서는 덮어쓴다** — "(정정)", "(2차 정정)" 같은 덧붙임 금지. 바뀐 이유는 결정 기록에 쓰고 링크만 건다.
3. **원칙마다 그것을 깨면 실패하는 장치를 하나 붙인다** — 문장으로만 있는 원칙은 언젠가 조용히 깨진다(§6).
4. **결정 대기는 한 곳, 한도를 둔다** — 에이전트가 "가정"으로 앞서가지 않게(§4.3).
5. **프로젝트 규칙은 저장소 안에 완결한다** — 전역 설정·개인 스킬·다른 런타임에 의존하면 다른 기계·인수인계자에게서 규칙이 사라진다(§7).
6. **만드는 눈, 확인하는 눈, 멀리 보는 눈을 분리한다** — 구현·검증·리뷰는 다른 에이전트가 한다. 각 Task가 맞아도 Task 사이에서 모순이 생기고, 그건 리뷰만 잡는다(§4.4, §4.6).

## 3. 문서 구조 — 세 층

```
CLAUDE.md                 # 에이전트 진입점: 프로젝트 정체·절대 규칙·작업 규칙·프로젝트 값 (짧게)
docs/
  spec/                   # [현재 상태] 도메인별 "지금 이렇게 동작한다". 덮어쓰기.
    <domain>.md
  decisions/              # [결정] ADR. 결정 하나 = 파일 하나. 고치지 않고 대체만.
    0001-<slug>.md
    README.md             # 결정 목록(번호·제목·상태) 한 표
self-reviews/             # [리뷰] 전체 점검의 관찰 기록 (§4.6). 날짜별, 고치지 않음. 실행은 TODO로 옮긴 것만
memo.md                   # 사람의 생각 입력함 (처리되면 비움)
DECISIONS.md              # 사람이 내려야 할 결정 대기열 (한 곳)
TODO.md                   # 실행할 Task (완료되면 삭제)
# 이력 = git log. archive 파일을 두지 않는다.
```
> ⚙ 폴더·파일 이름은 기본값이다. 🔒 "세 층을 섞지 않는다"와 "archive를 두지 않는다"는 불변이다.

### 3.1 현재 상태 문서 (`docs/spec/`)
- **질문**: "지금 시스템은 어떻게 동작하나?"
- **규칙**: 항상 참이어야 한다. 바뀌면 본문을 고친다. 과거 서술·정정 이력을 남기지 않는다.
- **에이전트가 매 세션 읽는 문서는 CLAUDE.md + 해당 도메인 spec뿐**이 되게 한다.
- 길어지면 쪼갠다(⚙ 한 파일 300줄을 넘으면 신호).

템플릿:
```markdown
# <도메인> — 현재 사양

> 최종 갱신: YYYY-MM-DD · 관련 결정: [0012](../decisions/0012-...md), [0031](...)

## 무엇을 하는가
(2~5줄)

## 규칙 (지금 유효한 것만)
- 규칙 A — 근거: [0012]
- 규칙 B — 강제 장치: `tests/test_xxx::test_rule_b`

## 화면·경로·데이터
(표)

## 알려진 한계
(지금 받아들인 것만. 해결되면 지운다)
```

### 3.2 결정 기록 (`docs/decisions/`, ADR)
- **질문**: "왜 이렇게 정했나?"
- **규칙**: 한 번 쓰면 고치지 않는다. 뒤집히면 **새 ADR**을 쓰고 옛 ADR의 상태만 `대체됨 → 00NN`으로 바꾼다.
- "왜?"가 필요할 때만 찾아 읽는다(매 세션 읽지 않는다).

템플릿:
```markdown
# 00NN. <결정 제목>

- 상태: 유효 | 대체됨 → 00MM | 폐기
- 날짜: YYYY-MM-DD · 결정자: <사람>

## 맥락
무엇이 문제였나 (3~6줄)

## 결정
무엇을 하기로 했나 (한 문단)

## 버린 대안
- 안 X — 버린 이유

## 결과
- 영향받는 spec: docs/spec/<domain>.md
- 강제 장치: (테스트·hook·설정 — 없으면 "없음"이라고 명시)
```

### 3.3 이력
- **git 커밋 메시지가 이력이다.** 커밋 메시지에 "무엇을·왜"를 쓴다.
- **완료 Task를 누적하는 archive 파일을 만들지 않는다.** 누적 파일은 반드시 낡고, 에이전트는 그것을 현재 규칙으로 오해한다. "읽지 말 것" 같은 경고문은 문장 규칙이라 검색 결과에 계속 섞인다 — 파일이 없는 것이 유일하게 확실한 방지책이다.
- 완료 처리 때 남길 가치가 있는 판단은 **ADR로 승격**하고, 나머지는 TODO에서 삭제한다.

## 4. 작업 흐름

```
memo(생각) ──> DECISIONS.md(결정 대기) ──> TODO(Task + 완료 조건)
                                              │
                        구현 에이전트(격리된 작업 공간)
                                              │
                        검증 에이전트(반박 관점)
                                              │
            커밋 + spec 갱신 + (필요하면) ADR 1개 ──> TODO에서 삭제

   ┌──────────── 주기적으로 / 마일스톤 직전 ────────────┐
   │ 리뷰(전체 점검) ──> self-reviews/<날짜>.md(관찰 기록)  │
   │        └──> 사람이 검토 ──> memo / DECISIONS / TODO   │
   └────────────────────────────────────────────────┘
```

| 역할 | 질문 | 범위 | 시점 |
|---|---|---|---|
| 구현 | 만든다 | Task 하나 | 매 Task |
| 검증 | **이 Task를 맞게 만들었나?** | Task 하나의 완료 조건 | 매 Task 완료 시 |
| 리뷰 | **전체적으로 맞는 것을 만들고 있나?** | 프로젝트 전체 — Task 사이, 문서↔코드, 원칙↔구현, 시스템↔시스템 | 주기적으로 + 마일스톤 직전 |

### 4.1 memo → TODO
- 사람은 memo에 자유롭게 쓴다. 에이전트가 읽고 **결정이 필요한 것은 DECISIONS.md로, 실행 가능한 것은 TODO로** 나눈다. 처리된 memo 항목은 지운다.

### 4.2 TODO Task 형식 — "사용자 언어 완료 조건"이 핵심
감독자가 코드를 읽지 않으므로, **완료 여부를 사람 문장으로 판정**할 수 있어야 한다.

```markdown
### T-042 — <제목>
- 왜: (한두 줄)
- 완료 조건 (사용자 언어):
  - [ ] 사내 일반 계정으로 로그인하면 메타데이터 목록이 보인다
  - [ ] 사외 계정은 배정 안 된 게임 이름을 어디서도 볼 수 없다
- 강제 장치: 위 조건마다 테스트 이름 (에이전트가 채움)
- 영향 spec/ADR: docs/spec/permission.md
- 의존: T-040
```

### 4.3 결정 대기열 (`DECISIONS.md`)
- 사람이 내려야 할 결정은 **이 파일 한 곳에만** 둔다. memo·TODO·spec에 흩어두지 않는다.
- 항목 형식: `D-NN | 무엇을 정해야 하나 | 선택지(★추천) | 안 정하면 무슨 일이 생기나 | 막고 있는 Task`
- **WIP 한도**(⚙ 기본 10건): 한도를 넘으면 에이전트는 새 기능 Task에 착수하지 않고 결정 요청을 먼저 한다.
- **가정 금지**: 결정이 필요한 지점을 에이전트가 "가정"으로 구현하지 않는다. 불가피하면 가정을 DECISIONS.md에 등록하고, 그 가정을 깨면 실패하는 테스트를 같이 만든다.

### 4.4 구현 에이전트 / 검증 에이전트 분리
- **구현 에이전트**: Task 하나를 받아 구현 + 테스트 + spec 갱신까지.
  - 병렬로 여러 개를 돌릴 때는 **격리된 작업 공간**(git worktree — Claude Code의 서브에이전트 `isolation: "worktree"`)을 준다. 커밋 혼입·파일 덮어쓰기·서버 충돌을 구조적으로 막는다.
- **검증 에이전트**: 구현 에이전트의 "완료" 보고를 **믿지 않는 관점**으로 확인한다.
  - 완료 조건 각각을 실제로 확인(테스트 실행, 화면 확인, 코드 대조)했는가
  - spec이 실제 동작과 일치하는가, 기존 ADR과 충돌하지 않는가
  - 보고서에 "확인함 / 추정" 구분
  - 사람의 코드 리뷰를 이 단계가 대신한다. **치명·높음 주장은 메인 세션이 직접 재확인**한다.

### 4.5 완료 처리
- 커밋(무엇을·왜) → spec 본문 갱신 → 필요하면 ADR 1개 → TODO에서 삭제. 끝.

### 4.6 리뷰 — 전체를 멀리서 보는 점검

검증이 "이 Task가 완료 조건을 채웠나"를 본다면, 리뷰는 **"각 Task가 다 맞았는데도 전체가 틀어진 곳"**을 찾는다. 원칙이 시드·기본값에서 조용히 깨진 곳, 두 기능이 같은 사실을 다르게 말하는 곳, 주인 없는 절차, 운영으로 가는 길의 공백 같은 것들은 Task 단위 검증을 전부 통과한 채로 쌓인다.

**언제 하나**
- **마일스톤 직전** — 오픈·배포·인수인계·외부 요청서 발송 전. (가장 가치가 크다)
- **주기적으로** — ⚙ 기본: Task 20개마다 또는 2주마다. 자율 진행이 할 일을 다 끝냈을 때도 좋은 시점이다.
- **큰 결정 전** — 아키텍처·시스템 간 역할 분담처럼 되돌리기 비싼 결정.
- **가벼운 변형: 설계 리뷰** — 큰 Task를 착수하기 전에, 구현 계획만 놓고 "기존 원칙·ADR·다른 기능과 충돌하나"를 한 에이전트가 반박 관점으로 본다.

**어떻게 하나 (절차)** 🔒 순서는 불변, 관점 선택과 수는 ⚙
1. **인터뷰** — 문서로 알 수 없는 맥락(성공 기준, 사용자·규모, 인력, 보안·조직 제약, 감독자가 불안한 점, 문제 제기 불필요한 것)을 사람에게 먼저 묻는다. 답은 기록해 모든 리뷰어가 공통 전제로 읽는다. **리뷰 품질은 이 단계가 좌우한다** — 코드는 "무엇을"만 알려주고, "그게 맞는지"는 목적을 알아야 판단된다.
2. **관점별 병렬 리뷰** — 서로 다른 전문가 관점의 리뷰어 여러 명을 동시에 돌린다(아래 목록에서 ⚙ 기본 4~6개). 각자 읽기 전용, 파일 수정 금지, 발견마다 근거(파일:줄)와 확인/추정 구분.
3. **교차 검증** — 메인 세션이 ① 여러 관점이 같은 곳을 가리킨 발견을 표시하고(신뢰도 높음) ② 치명·높음 주장은 **직접 코드로 재확인**한다. 틀린 주장은 정정 기록을 남긴다. 리뷰어도 틀린다.
4. **근본 원인으로 재구성** — 발견을 나열하지 않고 원인별로 묶는다. 원인 하나를 고치면 발견 여러 개가 같이 사라진다.
5. **보고서** — `self-reviews/<날짜>.md`: 한 페이지 결론 → 성공 기준별 판정 → 근본 원인 → 권고 로드맵(비용 작은 것부터) → **사람이 내릴 결정 목록** → 잘 된 점 → 재확인 기록. 관점별 원문은 부록으로.
6. **착수하지 않는다** — 리뷰 결과는 **관찰 기록**이다. 사람이 읽고 memo/DECISIONS/TODO로 옮긴 것만 실행된다. 리뷰어가 곧바로 고치기 시작하면 리뷰가 아니라 또 하나의 구현이 되고, 감독자는 결정권을 잃는다.

**리뷰 관점 목록 (⚙ 골라 쓴다)**

| 관점 | 찾는 것 |
|---|---|
| 도메인·업무 흐름 | 실제 사람 입장에서 처음부터 끝까지 따라가며 끊기는 지점, 주인 없는 단계, 상태 조합 모순, 알림·전파 부재 |
| 권한·보안 | 라우트 전수 대조, 격리 누수, 계정 생명주기, 감사·접근 이력, 보안 심의 격차, 기본값의 fail-open |
| 시스템 경계·R&R | 인접 시스템과의 계약 불일치, 한쪽에서만 내려진 결정, 역할 분담 대안 비교 |
| 운영 전환 준비도 | 오픈까지의 크리티컬 패스, 첫 구축 절차, 장애 감지·런북·백업, 비개발자 운영 가능성 |
| 지속가능성·검증 체계 | 테스트가 보장하는 것/못 하는 것, 문서 모순·낡음, 맥락 복원 비용, 과설계, 프로세스 사고 이력 |
| 사용자 경험 | 실제 계정별로 화면을 띄워 페르소나(비개발자 포함)의 여정을 확인 |
| 원칙↔구현 대조 | 문서에 "확정"으로 적힌 원칙이 시드·기본값·저장 방식에서 실제로 지켜지는가 |

**리뷰어 공통 지시(프롬프트에 넣을 것)**
- 단순 코드 리뷰가 아니라 **로직 모순, 프로세스 부재, 구조적·근원적 문제**를 찾는다.
- 인터뷰 기록을 판단 전제로 쓴다.
- 읽기 전용. 서버·DB·git 쓰기 금지. 비밀정보 파일 열람 금지.
- 발견마다: 제목 / 심각도(치명·높음·중간·낮음) / 관찰(근거) / 누가 어떤 상황에서 겪나 / 근원 원인 / 권고. 확인·추정 구분.
- 상세는 파일로, 최종 응답은 상위 N개 요약.

**비용 관리** — 리뷰는 사용량이 크다. 관점 수를 프로젝트에 맞게 줄이고(관련 있는 것끼리 합치기), 사용량 상한(⚙ 기본: 한도의 95%에서 즉시 중단, 그때까지 찾은 것만 기록)을 둔다. 마일스톤 직전 리뷰는 아끼지 않는 편이 결과적으로 싸다 — 오픈 뒤에 발견하면 비용이 몇 배다.

## 6. 기계적 강제 장치 — 문장 규칙을 장치로

**🔒 원칙: 사고가 한 번 나면, 재발 방지는 문장이 아니라 장치로 만든다.** 어떤 장치를 쓸지는 ⚙.

| 종류 | 무엇을 막나 | 예 |
|---|---|---|
| **원칙 테스트** | 선언한 원칙이 코드·시드·기본값에서 깨지는 것 | "조회는 전원 개방" → 권한 없는 신규 사용자로 조회 성공을 검사 / "환경변수 누락 시 잠금" → 변수 없이 앱을 만들면 잠금 상태인지 검사 |
| **전수 테스트** | 새로 추가된 것이 규칙을 빠뜨리는 것 | 모든 라우트가 권한 마커를 가졌는지 / 모든 메뉴가 환경 게이트를 가졌는지 |
| **운영 DB 테스트** | 테스트 DB와 운영 DB 방언 차이로 숨는 버그 | 가벼운 DB로만 돌면 FK 미강제·방언 차이를 못 잡는다 → 커밋 전 1회는 운영과 같은 DB로 |
| **hooks** (Claude Code) | 에이전트가 위험한 명령을 실행하는 것 | 프로세스 강제 종료, 전체 `git add`, 공유 DB 쓰기 명령 등을 실행 전에 차단 |
| **CI** | 로컬에서 안 돌린 검증 | push 시 전체 테스트 |

### 6.1 hooks

**🔒 hook 스크립트는 프로젝트가 이미 쓰는 런타임으로 작성한다.** Python 프로젝트는 Python, Node 프로젝트는 Node. hook 하나 때문에 다른 런타임 설치를 요구하면 원칙 5(저장소 안에서 완결)가 깨진다. 셸 스크립트는 OS(Windows/macOS/Linux)마다 동작이 달라 피한다.

**동작 명세 (언어 무관 — 이것만 지키면 어떤 언어로 써도 된다)**

| 항목 | 규약 |
|---|---|
| 등록 | `.claude/settings.json`의 `hooks.PreToolUse`에 `matcher: "Bash"`로 등록 |
| 입력 | stdin으로 JSON을 받는다. 검사할 명령은 `tool_input.command` |
| 차단 | **종료 코드 2**로 끝내고, 이유를 **stderr**에 쓴다 — 에이전트가 이유를 읽고 다른 방법을 찾는다 |
| 통과 | 종료 코드 0 |
| 차단 목록 | 스크립트 맨 위에 (패턴, 이유) 목록으로 모은다 |

**⚙ 차단 목록은 그 프로젝트의 사고 이력에서 채운다.** 아래 예시의 두 패턴은 출처 프로젝트에서 실제로 난 사고(사용자 서버 강제 종료, 전체 add로 인한 커밋 혼입)를 반영한 것이다 — 그대로 쓰지 말고, 같은 종류 사고가 두 번 나면 목록에 추가한다.

**적용 전에 해당 OS에서 동작을 반드시 시험한다**(차단돼야 할 명령과 통과돼야 할 명령을 하나씩 실행해 본다). 아래 두 예시는 macOS(Node 26, Python 3.12)에서 stdin JSON을 직접 넣어 차단 4건(`git add -A`, `git add .`, `taskkill`, `kill -9`)·통과 2건(`git add -- <경로>`, `git status`)을 확인했다(2026-09-26). **Claude Code에 hook으로 등록한 상태의 동작과 Windows는 검증하지 않았다.**

settings.json (런타임에 맞게 `command`만 바꾼다):
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "node .claude/hooks/block-dangerous.mjs" }
        ]
      }
    ]
  }
}
```

Node 예시 — `.claude/hooks/block-dangerous.mjs`:
```js
const BLOCK = [
  [/\btaskkill\b|\bkill\s+-9\b|\bpkill\b/, "프로세스 강제 종료 금지 — 프리뷰 도구의 stop을 쓴다"],
  [/\bgit\s+add\s+(-A|--all|\.)(\s|$)/, "전체 add 금지 — 경로 지정 커밋을 쓴다"],
];

let input = "";
process.stdin.on("data", (chunk) => (input += chunk));
process.stdin.on("end", () => {
  const cmd = JSON.parse(input).tool_input?.command ?? "";
  for (const [pattern, reason] of BLOCK) {
    if (pattern.test(cmd)) {
      console.error(`차단: ${reason}`);
      process.exit(2);
    }
  }
  process.exit(0);
});
```

Python 예시 — `.claude/hooks/block_dangerous.py` (`command`: `python .claude/hooks/block_dangerous.py`):
```python
import json, re, sys

BLOCK = [
    (r"\btaskkill\b|\bkill\s+-9\b|\bpkill\b", "프로세스 강제 종료 금지 — 프리뷰 도구의 stop을 쓴다"),
    (r"\bgit\s+add\s+(-A|--all|\.)(\s|$)", "전체 add 금지 — 경로 지정 커밋을 쓴다"),
]

cmd = json.load(sys.stdin).get("tool_input", {}).get("command", "")
for pattern, reason in BLOCK:
    if re.search(pattern, cmd):
        print(f"차단: {reason}", file=sys.stderr)
        sys.exit(2)
sys.exit(0)
```
> 참고: 실행 파일 이름은 OS마다 다를 수 있다(예: macOS는 `python3`만 있는 경우가 많다). 팀이 쓰는 OS 전부에서 같은 `command`가 동작하는지 확인한다.

## 7. 규칙은 저장소 안에

- 프로젝트 작업 규칙은 **저장소의 `CLAUDE.md`와 `.claude/`(skills·agents·hooks·settings)** 에 둔다.
- 사용자 전역(`~/.claude/`)에는 **개인 취향만**(말투, 커밋 서명 등) 둔다. 전역 규칙을 "그대로 따른다"고 링크하면, 다른 컴퓨터·인수인계자·클라우드 세션에서 그 규칙이 조용히 빠진다.
- 반복 절차(예: 정기 리뷰, 자율 진행)는 **프로젝트 스킬**(`.claude/skills/<name>/SKILL.md`)로 저장소에 넣는다.
- 서브에이전트 역할(구현·검증·리뷰 관점별)은 **프로젝트 에이전트 정의**(`.claude/agents/<name>.md`)로 넣으면 매번 프롬프트를 새로 쓰지 않아도 된다. 리뷰 절차(§4.6) 전체는 프로젝트 스킬로 넣어 "리뷰해줘" 한 마디로 같은 품질을 재현하게 한다.

> 문서가 이미 쌓인 기존 프로젝트는 [ai-dev-workflow-migration.md](ai-dev-workflow-migration.md)를 먼저 따른다.

2. **프로젝트 값을 정한다** — §9의 기본값 목록을 보고, 조정할 것만 골라 `CLAUDE.md` "프로젝트 값" 절에 적는다. 특히 hook 런타임은 프로젝트 런타임에 맞춘다.
3. §5 템플릿으로 `CLAUDE.md`를 쓴다.
4. 첫 ADR `0001-adopt-this-playbook.md`를 쓴다(조정한 기본값과 이유 포함).
5. hooks(§6.1)와 CI를 처음부터 넣는다 — 차단 목록은 비어 있어도 되고, 사고가 나면 채운다.
6. 리뷰 주기(§4.6)를 정한다 — 첫 리뷰는 첫 마일스톤 직전.

### 8.1 점검 신호 (정기적으로)
- 에이전트가 매 세션 읽는 필수 문서가 **⚙1만 토큰**을 넘는가 → spec 정리
- 결정 대기가 **WIP 한도**를 넘는가 → 결정 세션을 먼저
- 같은 종류 사고가 **두 번** 났는가 → 문장 규칙을 장치로(hook 차단 목록·테스트)
- spec에 "(정정)"이 생겼는가 → 본문을 고치고 ADR로 옮긴다
- 누적 기록 파일(archive류)이 생겼는가 → ADR로 승격하고 삭제
- 마지막 리뷰 이후 **리뷰 주기**가 지났거나 마일스톤이 다가오는가 → 리뷰(§4.6)
- 리뷰 결정 목록이 처리되지 않은 채 다음 리뷰가 오는가 → 새 리뷰보다 결정이 먼저
